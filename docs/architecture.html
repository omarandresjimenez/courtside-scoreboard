Courtside Scoreboard — Architecture

A LAN-first badminton scoring system: one server on one machine runs a whole tournament with no internet required, with optional internet delivery (live video + a public scoreboard) layered on top. Click any box below for how it's built, what it depends on, and what's tricky about it.

▸ How a video stream actually reaches someone across the world — the Court-side Phone → Firestore → Cloudflare TURN → Public Viewer path, step by step

The internet path exists because a viewer on another continent obviously can't reach a laptop on someone's home Wi-Fi. But the fix isn't "route the video through a cloud server" — it's WebRTC: the court-side phone and each viewer's browser open a direct peer-to-peer connection and stream video straight between them. Firestore is only ever used to help the two sides find each other; once connected, it never sees a single video byte.

  1. The court phone captures video.

    getUserMedia() grabs the phone's camera as a MediaStream. This needs a secure (HTTPS) context — the whole reason the server runs a second, TLS-only listener alongside its normal HTTP one.

  2. The broadcaster announces itself.

    It writes streams/{courtId} = { live: true } to Firestore — a tiny presence flag, not video — so any open viewer page flips from "waiting for the court to start streaming…" to "connecting" the instant the phone goes live.

  3. A viewer opens the public link.

    Anyone with the public URL loads a plain static page (no build step, no framework, hosted on Firebase Hosting) and creates its own document: streams/{courtId}/viewers/{viewerId}, stamped with a timestamp.

  4. The broadcaster starts a private negotiation with that one viewer.

    The phone watches the viewers subcollection live. The moment a new viewer document appears, it creates a brand-new RTCPeerConnection just for that viewer (a mesh, not a broadcast server — one connection per viewer, all from the same phone), attaches its camera track, and writes a WebRTC offer (an SDP blob describing its codec, resolution, etc.) into that viewer's document.

  5. The viewer answers.

    Its page is watching its own document for an offer field. When one shows up, it creates its own peer connection, sets the offer as the remote description, generates an answer, and writes that back to the same document.

  6. Both sides exchange ICE candidates.

    Each side gathers a list of possible network addresses for itself and writes each one as its own document, in offerCandidates / answerCandidates subcollections. Both sides are listening to the other's collection, so these arrive incrementally as real network paths to try.

  7. Direct connection is attempted — and usually needs help.

    Two random devices on the internet are almost always behind NAT, and a phone on cellular data is often behind carrier-grade NAT, which is stricter still. STUN (stun.l.google.com) only tells each side its own public address — it can't force a connection through a NAT that refuses unsolicited traffic. When that fails, the connection needs a TURN relay: a server both sides can reach that just forwards packets between them.

  8. TURN credentials are minted server-side — for the broadcaster only.

    The phone (not the viewer) asks the LAN server for one via GET /api/turn-credentials. The server calls Cloudflare's Realtime TURN API with a long-lived secret key that never leaves the server, and gets back a short-lived username/password pair (24h TTL) to hand to the browser. This is deliberately asymmetric: in ICE, only one side needs to offer a relay candidate for the connection to succeed, so the public viewer page needs no credentials — and no secrets — at all.

  9. Media flows — encrypted, peer-to-peer (or peer-via-relay-to-peer).

    Once ICE picks a working path, it's WebRTC doing what it does: encrypted (SRTP) audio/video streaming directly from the phone's encoder to the viewer's <video> element. If a direct path worked, it's true P2P; if TURN was needed, it's phone → Cloudflare relay → viewer — but still never through this app's own server.

  10. The score rides along on the same page, completely separately.

    Every point the umpire scores is mirrored (fire-and-forget, after the LAN broadcast) to a matches/{courtId} Firestore document through an explicit allow-list function — deliberately not a raw copy of the match, since the real record carries the umpire's scoring credential. The public viewer has its own separate live listener on that document, so the scoreboard updates regardless of whether the video connection is even up.

The limits, on purpose

  • ~5 viewers, hard cap. It's a mesh, so the phone runs a separate video encode per viewer. A 6th request is just refused — past that point, quality degrades for everyone, including people on the LAN.
  • Abandoned viewers get cleaned up. A crashed or killed tab never fires a proper "goodbye," so stale viewer documents older than 60 seconds are purged before being treated as real — otherwise a few dead tabs would permanently occupy all 5 slots.
  • Auto-reconnect, no manual reload. If the connection drops, the viewer page retries with backoff on its own.
  • Graceful degradation everywhere. No Firebase credentials → no internet path at all, but the LAN screens work exactly as before. No TURN configured → still works for anyone whose network allows a direct path; only the "someone's on hostile mobile-carrier NAT" case fails, with an on-page diagnostic explaining exactly that instead of a generic error.
